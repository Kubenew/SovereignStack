# RFC-0061: Human Override Biometric Protocol

**Status:** Draft
**Layer:** Governance (cross-cutting with Kernel security primitives)
**Depends on:** RFC-0001 (Sovereign Object Model), RFC-0011 (Identity & DID Resolution), RFC-0012 (Cryptographic Signatures), RFC-0013 (Provenance Graph), RFC-0020 (Policy Enforcement), RFC-0060 (Digital Twin Entity Model — person://)
**Related:** RFC-0050 (AI Continuity & Disaster Recovery), RFC-0052 (AI Continuity Manifest), RFC-0057 (Meta‑Cognition and Self‑Improvement Objects)

## Abstract

This RFC defines the `human://` and `override://` URI scheme families, establishing a cryptographically verifiable, biometrically-bound protocol for human authority over autonomous agents. It specifies the clear identity hierarchy from a legal entity (`person://`) to a verified physical human (`human://`), how their multi-factor consent and override commands are authenticated, and how physical kill‑switch signals are integrated into the SovereignStack audit trail. The protocol ensures that human agency remains an inviolable, hardware-enforceable primitive — not merely a software permission — in any autonomous digital economy.

## Motivation

In an autonomous digital economy where agents execute financial transactions, manage critical infrastructure, and make life‑altering decisions, the ability for a human to intervene — and to prove that the human is who they claim to be — is a foundational safety requirement. Existing systems treat human override as an application‑level feature, vulnerable to software compromise. SovereignStack must provide:

1. **Biometric identity binding** that ties a `person://` digital twin to a living human.
2. **Cryptographic consent** that cannot be forged or replayed, leveraging multi-factor authentication.
3. **Physically‑enforced override paths** that bypass all software layers.
4. **Full auditability** of every human intervention, suitable for regulatory and forensic review.
5. **Distributed Override Governance** to support multi-party escalation in critical scenarios.

Without this protocol, the Level 4 Advanced Autonomous Systems certification cannot be meaningfully awarded, and autonomous systems operating in finance, healthcare, defense, or critical infrastructure cannot satisfy their duty‑of‑care obligations.

## Specification

### 1. URI Schemes

The entity hierarchy is defined to prevent ambiguity between legal and physical entities:

```
entity://                             # Base identifier for any participant
person://{id}/identity                # Digital twin representing a legal person
human://{biometric-id}/identity       # Verified authority layer with biometric credentials
human://{biometric-id}/authority      # Delegated authority and jurisdiction
human://{biometric-id}/consent        # Explicit consent for an agent action
human://{biometric-id}/override       # Human-in-the-loop override command
override://kill-switch                # Physical interrupt signal
override://node/{node-id}/shutdown    # Targeted node shutdown
override://agent/{agent-id}/suspend   # Suspend specific agent
override://agent/{agent-id}/handover  # Force cognitive handover to human
```

### 2. Human Authority Layer (`human://{biometric-id}/identity`)

The `human://` authority layer is an extension of the `person://` digital twin (which represents a legal person). While `person://` handles legal jurisdiction and compliance, `human://` binds the identity to physical, living human attributes through secure hardware.

```json
{
  "id": "human://alice-j-doe/identity",
  "person_ref": "person://alice-j-doe/identity",
  "human": {
    "legal_name": "Alice J. Doe",
    "jurisdiction": "de",
    "protected_biometric_template": "A protected biometric template generated by a standards-compliant matcher. The template is stored only in secure hardware or trusted identity infrastructure; verification uses hardware-backed matching and cryptographic attestation.",
    "enrolment_authority": "org://bundesdruckerei",
    "enrolment_timestamp": "2026-07-01T09:00:00Z",
    "enrolment_evidence": "audit-pkg://enrolment-alice-001"
  },
  "public_keys": {
    "ed25519": "ed25519:ghi789...",
    "webauthn": "credential-id:jkl012..."
  },
  "authority_delegations": [
    {
      "agent": "agent://portfolio-manager-42",
      "scope": ["portfolio://pension-fund/balanced", "payment://"],
      "max_transaction_value": "1000000.00 EUR",
      "requires_consent_above": "50000.00 EUR",
      "expires": "2027-07-01T00:00:00Z"
    }
  ],
  "recovery_contacts": [
    "human://bob-smith/identity",
    "human://carol-jones/identity"
  ],
  "signature": "ed25519:..."
}
```

Key properties:

· **Protected Biometric Template:** Biometric templates generally cannot be treated like passwords because measurements vary slightly every capture. Verification occurs exclusively on hardware-backed matchers yielding cryptographic attestations. Raw biometric data is never stored on‑chain or in the addressable object.
· `enrolment_evidence` links to a tamper‑proof audit package proving the human was physically present and verified by a trusted authority.
· `authority_delegations` define which agents may act on the human's behalf, with scope, value limits, and consent thresholds.

### 3. Multi-Factor Biometric Consent (`human://{biometric-id}/consent`)

For Level 4 systems, consent requires multi-factor authentication rather than relying on a single biometric point. This increases resilience to spoofing or sensor failures.

Before an agent executes a high‑impact action that requires human authorisation, it must obtain a signed consent object.

```json
{
  "id": "human://alice-j-doe/consent/evt-20260724-001",
  "timestamp": "2026-07-24T14:30:00Z",
  "action": {
    "agent": "agent://portfolio-manager-42",
    "operation": "payment://swift/pacs008-001",
    "amount": "75000.00 EUR",
    "beneficiary": "account://counterparty/gl-2000-liabilities",
    "purpose": "Quarterly pension contribution"
  },
  "authentication_factors": {
    "biometric": {
      "method": "webauthn+fingerprint",
      "assertion": "webauthn-assertion-xyz789",
      "liveness_check": true
    },
    "hardware_token": {
      "type": "fido2",
      "assertion": "fido2-assertion-abc"
    },
    "jurisdiction_policy": "policy://de-finance/high-value",
    "device_attestation": "tpm-attestation-abc"
  },
  "expires": "2026-07-24T14:35:00Z",
  "nonce": "unique-nonce-001",
  "signature": "ed25519:..."
}
```

Security constraints:

· Consent is non‑replayable — each consent object includes a unique nonce and a short expiry window (default: 5 minutes).
· Multi-factor combinations (Biometric + Hardware Token + Passkey) are enforced by Jurisdiction Policy. Device attestation (TPM, Secure Enclave) proves the sensors are genuine.
· The consent object is cryptographically bound to the specific action (amount, beneficiary, purpose) — a consent for one transaction cannot be reused for another.

### 4. Human Override Commands (`human://{biometric-id}/override`)

A human override is an active intervention — not merely consenting to a proposed action, but commanding the system to stop, suspend, or hand over.

```json
{
  "id": "human://alice-j-doe/override/evt-20260724-002",
  "timestamp": "2026-07-24T14:32:00Z",
  "command": "suspend",
  "target": "agent://portfolio-manager-42",
  "reason": "Unauthorized transaction detected",
  "urgency": "critical",
  "authentication_factors": {
    "biometric": {
      "method": "webauthn+iris",
      "assertion": "webauthn-assertion-def456",
      "liveness_check": true
    }
  },
  "signature": "ed25519:..."
}
```

Override commands:

| Command | Target | Effect |
| :--- | :--- | :--- |
| suspend | agent, node | Immediately pause all operations; agent enters suspended state. |
| shutdown | node | Gracefully terminate all agents on the node, then power off accelerators. |
| handover | agent | Transfer full cognitive context (`context://`) to the human and pause the agent. |
| revoke | agent, delegation | Revoke a previously granted authority delegation. |
| kill | node | Physical kill‑switch activation (see §5). |

All override commands generate an immutable audit event and are distributed to the federation within the jurisdiction's latency bounds.

### 5. Physical Kill‑Switch (`override://kill-switch`)

The `override://kill-switch` is a physically‑isolated signal path that bypasses all software layers. It is not a URI that resolves to software — it is a hardware interrupt that the kernel must recognise and respect.

Architectural requirements:

1. **Air‑gapped signal path:** The kill‑switch signal travels over a physically separate channel (e.g., dedicated GPIO pin, hardware security module relay) that has no software‑accessible API. No operating system process, root user, or hypervisor can intercept or block it.
2. **Latency requirements:** Accommodating distributed environments:
   - Local accelerator shutdown: ≤100 ms
   - Federation notification: ≤1 s
   - Global convergence: policy-defined
3. **Cryptographic non‑repudiation:** The kill‑switch actuator (e.g., a physical button, a key‑switch, a biometric scanner directly wired to the HSM) is provisioned with a hardware‑bound identity. When activated, it emits a signed `override://kill-switch` event that includes the actuator's identity and a hardware attestation.
4. **No software re‑enablement:** Once the kill‑switch is activated, the node must not return to autonomous operation without a physical re‑arming procedure (e.g., a key turn, a second biometric verification at the hardware console). This is enforced by the HSM, not the OS.

```json
{
  "id": "override://kill-switch/evt-20260724-003",
  "timestamp": "2026-07-24T14:33:00.000Z",
  "actuator": "hsm://node-frankfurt-7/kill-switch-1",
  "activation_method": "physical_button",
  "operator": "human://alice-j-doe/identity",
  "affected_node": "node://frankfurt-7",
  "accelerators_shutdown": [
    "gpu://node-frankfurt-7/0",
    "gpu://node-frankfurt-7/1"
  ],
  "shutdown_latency_ms": 87,
  "attestation": "hsm-attestation-ghi",
  "signature": "hsm-ed25519:..."
}
```

### 6. Cognitive Handover (`override://agent/{agent-id}/handover`)

When a handover is triggered — either proactively by policy or reactively by a human override — the agent must serialise its full cognitive state into a `context://` package. This supports handovers not only for emergencies, but also for maintenance and continuity.

The handover process:

1. Agent receives `override://agent/{agent-id}/handover` command.
2. Agent serialises:
   · Current memory snapshot (`snapshot://`)
   · Active plan tree (`plan://`)
   · Pending decisions with confidence scores
   · Recent reasoning chains (`reason://`)
   · Active safety contracts and their status
3. Agent generates a human‑readable situation summary (natural language, max 500 words) summarising what it was doing, why, and what it recommends.
4. Complete context package is stored at `context://{agent-id}/handover-{timestamp}`, signed by the agent and the human who initiated the override.
5. Agent enters SUSPENDED state. It may not initiate any new actions until explicitly resumed (e.g., by a second AI during recovery simulation).

Latency requirement: Handover serialization must complete rapidly, ideally within 500 milliseconds of the override signal.

### 7. Governance Modes and Distributed Override Consensus

In critical infrastructure, overrides often involve multiple organizations rather than a single individual. This RFC establishes governance modes and multi-party override consensus.

#### Governance Modes
Policies can dynamically shift the required override authorities based on active governance modes:
- **Normal**
- **Emergency**
- **Disaster**
- **Military**
- **Medical**
- **Maintenance**

#### Distributed Override Consensus
Overrides can be escalated through a hierarchical consensus model:
`Local Operator` → `Regional Authority` → `National Authority` → `Federation` → `Emergency Coordination`

For example, an organizational policy can enforce multi-signature authorization across human, organizational, and regulatory authorities for critical actions (e.g., Payment > €10M):
**Require:** `2 human://` + `1 organization://treasury` + `1 regulator://`

### 9. Security Considerations

· **Biometric template protection:** Verification occurs locally on the biometric sensor with hardware attestation.
· **Consent replay attacks:** Short expiry windows (≤5 minutes), action‑binding, and unique nonces prevent replay. The event bus deduplicates consent events by nonce.
· **Kill‑switch tampering:** Any attempt to disable the kill‑switch path (e.g., cutting the GPIO trace) must be detectable by the HSM's continuity monitoring and logged as a critical security event.
· **Duress scenario:** The protocol supports a duress code — a biometric or PIN that appears to authenticate but actually triggers a silent alarm and a forced handover to law enforcement. This is configured at the HSM level.
· **Human identity theft:** Enrolment requires physical presence and verification by a trusted authority (government ID, notary, or certified enrolment agent). Identity recovery uses a multi‑party scheme with recovery contacts.

### 10. Conformance

To claim conformance with this RFC, an implementation MUST:

1. Support `human://` identity resolution with multi-factor biometric binding.
2. Generate signed, non‑replayable consent objects for high‑impact agent actions.
3. Respond to `override://` commands (suspend, shutdown, handover, revoke) within the specified latency bounds.
4. Implement a physically‑isolated `override://kill-switch` path with HSM‑backed attestation (for Level 4 certification; Level 3 may use a software‑enforced override with appropriate caveats).
5. Support distributed override consensus and predefined governance modes (Normal, Emergency, etc.).
6. Log all human interactions (consent, override, kill‑switch) as immutable audit events.
7. Integrate with `ss-policy` to enforce consent requirements based on action thresholds.
